## Boundaries

- Website: `/api/newsletter` is code-paused. Confirmation and unsubscribe GETs only render a form; POST proxies a protected capability to an exact regional API Gateway origin. Vercel receives a dedicated bridge secret, never AWS access keys. Invalid/missing infrastructure returns a truthful 503 with support recovery instructions.
- API Gateway → API Lambda: authenticated server bridge; explicit versioned consent; one confirmation request per address per UTC day, ten per client fingerprint per UTC hour; mailbox confirmation expires after 24 hours. There is no public reactivation or suppression-removal path.
- DynamoDB: authoritative consent, subscriber state, immutable request/confirmation/suppression audit, migration provenance, durable article backlog/identity and canonical URL claims, frozen campaign articles, per-recipient claims and processed feedback identifiers. Only rate-limit entries expire. There is no automatic deletion of consent, suppression or article idempotency evidence.
- DynamoDB stream → contact-sync Lambda: retries mirror consent/suppression into the dedicated SES Contact List. Existing SES opt-outs are never changed to opt-in. Failed sync cannot make a recipient eligible for sending.
- EventBridge Scheduler → planner SQS → planner Lambda: Monday 09:00 UTC; fetch the complete public `https://chronoversecapital.com/rss.xml` archive. Freeze **up to ten**, oldest eligible first, with durable backlog and cross-issue ID/URL claims. First approved execution starts at the prior Monday 09:00 UTC; subsequent executions include missed weeks and unsent overflow up to the current closed boundary (`[start, end)`). Fewer than five are used if fewer qualify; no historical filler. Empty/unavailable/invalid feeds cannot create campaign mail. Pagination uses 16 audience shards and 100-record pages with queued continuations. See the [RSS discovery report](../../docs/newsletter-rss-discovery-2026-10-24.md).
- Digest SQS → worker Lambda: one recipient per message, per-campaign atomic claims and fresh suppression/opt-in checks before SES v2. A shared `RATE#SES_SEND_GATE` lease serializes all newsletter SES handoffs, including confirmations and direct adapter calls. The owner releases with a one-second cooldown after SES settles. An abandoned lease expires after 120 seconds, twice the deployed 60-second timeout; never raise that timeout without reviewing the lease. Both DynamoDB consent and explicit SES topic opt-in are required.
- SES configuration set → SNS → authenticated SQS → feedback Lambda: permanent bounces, complaints and topic/list opt-outs persist suppression; transient bounces do not. SNS `OPT_IN` events cannot clear the ledger. No open/click tracking is configured.

## Safety and retry semantics

All five infrastructure switches default to `false`; the SES configuration set has sending disabled and Lambda roles receive no `ses:SendEmail` permission until the relevant conditions are approved. Runtime checks additionally require a `CONTROL` ledger item. Its absence fails closed. Unsubscribe and feedback ignore mail-enable gates.

Confirmation activation requires exact `"true"` registration/confirmation/legacy-retirement/compliance runtime flags and boolean `true` for `registrationEnabled`, `confirmationEnabled`, `legacyRetired`, `complianceApproved`, `migrationComplete` in `CONTROL`. Historical suppression/recovery readiness must be approved even for a zero-audience launch; this does not authorize or require a legacy subscriber import. The persistence adapter revalidates the signed, unexpired token and atomically checks current control approval, changes only an unsuppressed `PENDING` record with its matching nonce, removes that nonce and inserts consent audit. Replayed/consumed/revoked tokens cannot activate again. Pause durable enrollment control first to cover in-flight invocations, then change infrastructure flags. Digest delivery may remain disabled during separately approved enrollment. No control/subscriber records are seeded by provisioning.

Before SES, a conditional DynamoDB claim becomes `CLAIMED`. Successful acknowledgement becomes `ACCEPTED`, which does not mean inbox delivery. SDK sending has **one attempt**. Only an explicit SES HTTP 429 rejection becomes `RETRYABLE`, capped at three attempts. Timeouts, missing message IDs, crashes and lost acknowledgements stay `UNKNOWN`/`CLAIMED` and are never automatically resent. Redriving queues cannot bypass an existing claim. Do not erase claims to retry. Review provider evidence separately.

A positively rejected local send-lease acquisition starts no SES request. Digest processing conditionally returns that claim to `RETRYABLE` and refunds that local attempt; it cannot reset `ACCEPTED`/`UNKNOWN` claims. SQS still has a five-receive/14-day retention bound and six-minute visibility; monitor contention and dead letters. Confirmation contention returns 503 with a `NOT_SENT` claim and leaves consent pending; it is not automatically queued or retried, and the existing per-address daily limit still applies. Enrollment remains blocked for live activation until this behavior and managed-service load tests are approved. Safety processing never takes the send lease.

An opt-out committed after the final check cannot recall mail already handed to SES. SES list enforcement and asynchronous feedback are additional safeguards, not an atomic transaction across AWS services. The 72-hour campaign lifetime prevents stale queued campaigns sending later. At roughly one message/second, 100,000 recipients need at least 27.8 hours plus overhead; larger audiences require a reviewed quota/concurrency change.

SQS retries and dead-letter retention are bounded. Stream failures also go to the failure queue. Four alarm groups cover eight billable metrics: regional Lambda Errors/Throttles, dead letters, one dimensionless SafetyFailure application metric, and all three queue ages plus contact-stream age. Regional execution alarms also cover unrelated functions; use native per-function metrics and bounded signal fields in logs for diagnosis. Hard bounces and complaints publish the fault signal after suppression. Normal diagnostics remain log-only; no successful unsubscribe is treated as a fault. Five log groups retain 14 days; durable consent/suppression history is unaffected. AlarmTopicArn is empty by default; an approved notification destination and incident owner remain activation gates. Logs contain bounded diagnostic categories only; never enable body/header/query logging or log subscriber addresses/tokens. Queue messages, DynamoDB and secrets are private; access to them is privileged. Approve retention and an incident handler before launch.

## State and migration

`DISCOVERY` retains the first approved period, including when its first fetch fails. `ARTICLE#sha256(guid)` holds every discovered eligible public article as `PENDING`; assignment to an immutable weekly campaign and `ARTICLE_URL#sha256(canonicalUrl)` claims commit atomically. At most ten become `ISSUED`; excess stays `PENDING` without TTL. `ISSUED` means inclusion in one frozen issue, not guaranteed SES delivery. Per-recipient delivery claims continue to hold uncertain outcomes rather than resend. Pending articles absent from the current full public feed are held, so retired/unpublished content is not resurrected from cached metadata. Changed original publication dates fail closed for review.

The full archive avoids a rolling-feed cutoff and needs no extra table, index, scheduler or newsletter webhook. Feed retrieval is bounded to 2 MB, 5,000 items and ten seconds; exceeding limits stops new issues instead of truncating articles. Monitor planner failures and archive growth before reaching those limits. Hosting migrations must retain public GUIDs, canonical domain and the retained DynamoDB ledger; do not reset `DISCOVERY`, article/URL claims, campaigns or per-recipient claims. See the RSS report for cutover and rollback checks.

`PENDING` → mailbox-confirmed `CONFIRMED` → permanent `SUPPRESSED`. Legacy imports enter `HOLD`, or `SUPPRESSED` when inactive, suppressed or known opted out. `HOLD` never receives a campaign or automatic reconfirmation mail. Re-enrolment needs a separately approved consent process; merely submitting signup again does not reopen a record.

`src/migration.mjs` is a pure offline deduplication planner. It accepts normalized records containing `sourceId`, `email` or `emailHash`, original active/suppressed/reason fields and consent evidence. Suppressions dominate duplicates, including hash-only legacy suppressions. Each original source reference/evidence is preserved in immutable migration provenance; retain the full original encrypted export separately as well.

`scripts/import.mjs` defaults to offline counts only. Its apply mode requires a separately approved input file, SHA-256, exact table ARN/account and region, and `--apply-approved`. It checks table metadata before writing, reserves an immutable batch digest, retains existing records, imports suppressions without reactivation and never sends mail. Use a dedicated assumed migration role, not the API role or shared Sanity credentials. Never run apply without separate production-data authorization.
