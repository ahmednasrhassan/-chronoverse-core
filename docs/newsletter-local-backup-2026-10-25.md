## Design and source findings

The utility is an owner-only Windows **terminal application**, separate from Next.js and Lambda packages. There is no browser UI/storage, HTTP endpoint, service installation, telemetry, public deployment or new AWS infrastructure. Keeping it out of the website avoids adding a public subscriber-export surface. SDK dependencies and lockfile are isolated under `tools/newsletter-backup/`.

| Requirement | Implementation |
| --- | --- |
| Authoritative subscription and consent | Full, strongly consistent paginated Scan of the dedicated DynamoDB ledger. `SUB#` provides email/state/request and confirmation data; `AUDIT#` supplies immutable request, consent text/version/source, confirmation and suppression evidence. `MIGRATION#` and batch records retain historical provenance. |
| Unsubscribe, hard bounce and complaint | Ledger suppression/audit and targeted SES account suppression checks for known newsletter addresses; paginated SES dedicated Contact List preserves explicit topic/list opt-outs. Suppression always wins, including hash-only historical negatives and conflicting duplicates. List defaults do not fabricate individual consent or unsubscribe. |
| Event recovery | Processed `EVENT#` markers and their available references are archived. Generic bounce markers are distinguished from confirmed hard-bounce suppression. The application does not persist all raw SES event details; this utility cannot reconstruct absent details or read unprocessed SNS/SQS messages. |
| Private authentication | Hidden backup passphrase plus an independently approved temporary assumed-role session from AWS CLI console login or existing SSO. Exact account/role/table/list checks; static keys, arbitrary credential processes/endpoints and root/IAM-user sessions rejected. No Secrets Manager or subscriber write/send permission. |
| Manual/automatic refresh | Interactive `s` refresh, stored counts/read window, explicit `a` for hourly completion-relative automatic attempts. Default inactive; no overlapping work. Failure pauses scheduling and preserves the previous successful backup/time. `p`/`q` cancel reads; shutdown drains before clearing keys. Closed/asleep/offline/powered-off time has no promised updates. |
| Encrypted snapshots | AES-256-GCM with authenticated format/purpose/KDF header and random per-file IV. Portable passphrase-derived scrypt key (`N=131072,r=8,p=1`). Owner/SYSTEM NTFS ACL, no reparse/cloud-sync/Git path, ciphertext-only atomic commit/readback and linked snapshot digests. AWS dates and binary attributes retain ISO/base64 wire values; numeric attribute strings retain precision. |
| Retention and offline recovery | No automatic deletion. Default 100 snapshots, up to 1,000 configured at initialization; 128 MiB active snapshot-chain limit / 64 MiB decoded-file limit. Manual local rotation carries latest data, historical evidence and cumulative suppressions into a new private vault, preserving the old archive and original read timestamp. Offline restore copies ciphertext and checks its chain/scope. |

No Brevo API/CSV upload or campaign execution is included. |

All complete ledger data, including send/article claims and durable control observations, remains encrypted for disaster-recovery investigation. **There is no cloud restore or control replay operation.** A future AWS restore must preserve uncertain sends/idempotency, reconcile fresh opt-outs, keep controls disabled and handle pending capabilities/unsubscribe keys under a separate approval.

## Verified limits and remaining security review

1. DynamoDB Scan lacks point-in-time isolation, even with strong reads; SES observations occur later. Snapshots state their read window and `atomicPointInTime=false`. Newly arriving opt-outs can postdate an observation. Recovery therefore never activates contacts. Managed PITR and a separately approved reconciliation remain necessary for authoritative full-system recovery. [AWS Scan semantics](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Scan.html)
2. No record currently comes from production. Temporary authentication, effective IAM, managed-service permissions and actual response sizes remain unverified. The policy example grants only dedicated table reads, contact-list reads and targeted account-suppression reads. SES requires a regional wildcard for the last operation; a compromised role could inspect other known addresses. The tool avoids account-wide recipient enumeration. Owner must verify that the chosen role has no other broad policies.
3. AWS CLI console login needs version 2.32+ and suitable existing identity permissions. Do not create users/keys, enable Organizations or upgrade the Free Plan just to configure this tool. Existing SSO is an alternative. Profile caches contain temporary credentials outside the vault; approve device/profile protection and MFA before integration. [AWS temporary console authentication](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html)
4. The passphrase/key and decrypted data exist in RAM; JavaScript/OS copies cannot all be erased. Use a trusted locked Windows account, encrypted device/pagefile and a separately held recovery passphrase. ACLs do not defend against administrator/malware compromise. There is no independent cryptographic/security audit claim.
5. Linked digests detect missing/reordered retained links, and AEAD detects tampering. They cannot prove freshness if an attacker deletes the entire latest suffix or substitutes a complete older vault. Maintain an independently trusted encrypted offline copy/checkpoint. Normal quit releases the owner lock; abrupt termination may leave a stale lock or ciphertext staging file requiring private review after all tool processes stop.
6. Raw legacy consent archives, original signing-key continuity and unprocessed feedback are separate responsibilities. No local backup restores unsubscribe rights by itself. Never import pending/legacy/ambiguous contacts into a sendable Brevo list or clear marketing blocklisting to make an import pass.

## Cost and operation

There are **no new fixed AWS charges**: no new Lambda, Scheduler, DynamoDB table, S3 storage, alarms, secret or subscription. Existing AWS resources are reused read-only. Variable usage is a full ledger scan plus existing authentication and targeted SES reads. At the previously verified Stockholm DynamoDB Standard rate, 10,000 billable RRUs cost approximately **$0.001345** before credits/allowances; actual scan consumption and history growth must be measured after approval. No account bill was inspected. Existing provider audit/data-event logging may capture API parameters or incur additional usage; its privacy/access/retention needs owner review. The utility does not alter those settings or claim that provider audit logs are PII-free. [Public regional pricing](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonDynamoDB/current/eu-north-1/index.json)

SES calls are at least two seconds apart, with at most three paced attempts for explicit throttling. This does not serialize other applications' account-wide API traffic. At 1,000 addresses, suppression checks alone take roughly 33 minutes, so this is a periodic owner backup, not a real-time replica. Choose an approved quiet window and stop on contention; do not weaken the newsletter's unsubscribe or provider checks. Local disk, passphrase custody and owner time remain costs. Credit expiry and all prior newsletter activation blockers remain unchanged.

Retention is explicit and conservative: no purge or upload is automatic. Approve a lawful local/offline backup retention schedule and review disk limits. Before a cap is reached, manually rotate to a new active vault and preserve the prior encrypted chain. Rotation does not refresh AWS observations. Offline copies should include the encrypted vault and complete chain; do not place subscriber backups into source-code backups or Git.
